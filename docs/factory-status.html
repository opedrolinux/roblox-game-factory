What T2.5 cannot see, stated by the rung itself: it runs in edit mode with no LocalPlayer, so the entire client — HUD, motes, leaderboard, the client bootstrap, whether a prompt is even reachable — is unverified. Physics does not step and the server clock is frozen, so nothing time-gated or jumpable can be asserted. A green here means "not obviously broken", not "ready to play". The rung re-asserts those limits every run and goes red when one lifts, so the day the engine starts stepping physics, somebody gets interrupted.

And that blindspot immediately cost something real. A client audit found the offline-earnings claim firing before the save finished loading — it failed, nothing retried, and autosave erased the away-window within 60 seconds, so the grant was lost permanently, worst for exactly the players it exists to serve. Every rung was green throughout. The fix (JoinRetry.once) could only be proven the way the missing rung would have: by driving Studio directly. Same published place, same build, minutes apart — the pre-fix run logged claim failed: NoData and stopped; the post-fix run recovered 54 Stardust on the data push, retrying exactly once even though the recovered claim itself triggers another push. That last part matters: the obvious one-line fix is an infinite remote loop here.

This ladder exists because of a real scar: collect-sim once passed 313 tests and still failed to boot in Roblox — a cross-service require that the simulator resolved and the engine didn't. T0.5 was built to catch that class statically. As of today it is caught at runtime too: the boot probe executed every one of those requires inside a real DataModel and none of them threw.

What the engine actually said

Five assumptions the code was built on. Four are now facts.

The persistence layer shipped with five TODO(verify) markers — claims about how Roblox behaves that three rounds of adversarial review could not settle, because no amount of reading code answers them. Running it does.

The assumptionWhy it matteredVerdict
Returning "don't write" to Roblox aborts the write, and doesn't raise an error If backwards, the crash-recovery logic silently inverts — and every test still passes green Holds
The same, for the durable store This is what stops a displaced server overwriting a record it no longer owns Holds
A 1-second lock expiry is accepted Otherwise a lock lingers 30s instead of 1s on every disconnect Holds
Cancelling an already-finished task is harmless An error escaping teardown would leave a player neither loaded nor kicked Holds
The server's unique ID is non-empty and unique It identifies which server owns your save. Empty in every Studio mode, so the fallback ID is what actually runs Needs live players

One genuine defect surfaced and turned out not to be ours: writing a lock with a 1-second expiry leaves a roughly one-second window where Roblox refuses to update it. Reproduced with raw engine calls and none of this project's code in the stack. It is intermittent, self-healing via the existing retry, and costs no data — but it is measured rather than assumed, which is the point.

One known defect, one fixed, and a missing suite

  • ✓ The offline-earnings claim was lost on join — fixed and proven Observed in 3 of 3 real Play sessions: the client asked before the save had loaded, got "no data", warned once and never retried. Worse than it looked — autosave rewrites the away-window within 60s, so the grant was lost permanently, not merely deferred. Fixed by a retry that fires exactly once on the load push (the obvious version loops forever, because the claim itself writes and every write pushes). Proven by driving Studio: same place, same build, minutes apart — before, it stopped at the failure; after, it recovered 54 Stardust.
  • 2 Buying the backpack upgrade does nothing Known-red in the T2.5 playtest, reported deliberately outside the pass/fail so it cannot become routine. Stardust is deducted and capacity stays at 50 — the constant is never reconciled against the purchased level.
  • 3 Build the security suite Rate limiting, validators, violation tracking. The game prints a warning about this on every single boot — it is not publish-safe until it lands.
Only you can do this

One, and it is the real gate

  • 4 Play it, with other people Three questions no automated rung can reach: is it any fun, does the client actually work with a real player in it, and does the save-lock hold when two real servers contend over one player? A single Studio session cannot contend with itself, by construction.

Honest read: both defects above are client-side or economy-side, and both were found by looking at a real session rather than by any test. That is the shape of what is left — the machine has verified the parts it can reach, and the parts it cannot reach are where the remaining bugs live. The offline fix is the proof of that in both directions: no rung could see it, and no rung could confirm the repair either — that took a real Play session.
